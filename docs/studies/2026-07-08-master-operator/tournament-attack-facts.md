## 1. The core dependency: Pydantic AI v2 + DBOS `DBOSAgent` — REAL, RELEASED, DOCUMENTED

**Claim (C2 §2, synthesis §2.1):** "Official `DBOSAgent` integration wraps `Agent.run` as a DBOS workflow and model requests as checkpointed steps."

**VERIFIED — the integration exists, is official on both sides, and is v2-current:**

- `DBOSAgent` lives at `pydantic_ai.durable_exec.dbos.DBOSAgent`; it "automatically wraps `Agent.run` and `Agent.run_sync` as DBOS workflows" and wraps model requests and MCP communication as DBOS steps. Install: `pip install pydantic-ai[dbos]`. Source: https://pydantic.dev/docs/ai/integrations/durable_execution/dbos/ (fetched 2026-07-10); mirrored on the DBOS side: https://docs.dbos.dev/integrations/pydantic-ai; announcement article: https://pydantic.dev/articles/pydantic-ai-dbos.
- **Pydantic AI v2 exists and is stable:** v2.0.0 released **2026-06-23** ("After seven betas, Pydantic AI V2 is now stable" — https://pydantic.dev/articles/pydantic-ai-v2). Release cadence since: 2.5.1 (Jul 6), 2.7.0 (Jul 8), 2.8.0 (Jul 10) — https://github.com/pydantic/pydantic-ai/releases. C2's "v2.6.0 released 2026-07-08" is within a version or two of exact; immaterial.
- Documented `DBOSAgent` caveats match what C2 reported: `Agent.run_stream()`/`run_stream_events()` unsupported inside a DBOS workflow (irrelevant for WhatsApp, as C2 said); custom tool functions NOT auto-wrapped (must be decorated `@DBOS.step` if they do I/O — the crm-adapter/rag-api calls in the turn workflow must remember this); DBOS pickles workflow inputs/outputs and step outputs into Postgres, keep payloads small (~2 MB advisory). Same page as above.
- DBOS durable queues "support concurrency limits, rate limits, timeouts, and prioritization" — the verbatim capability list C2 quotes is on the integration page. VERIFIED.

**Churn note (minor):** v2 was **15 days old** when the study committed to it, and v2.0→v2.8 shipped in ~17 days. v2 is an architectural reshape ("capabilities" superseding toolsets as the composition primitive; `DeferredToolCalls` renamed `DeferredToolRequests` — https://pydantic.dev/docs/ai/project/changelog/). The candidate docs use the *current* (v2) API names — good — but the Stage-0 spike must pin exact versions of both libraries and re-run on any bump.

## 2. Deferred tools (HITL primitive) — REAL and v2-current, but the RESUMPTION SEMANTICS ARE MIS-STATED in the design

**Claim (C2 §3 diagram; synthesis spike rubric item (b)):** "asesora approves in team surface → `DeferredToolResults` **resumes the SAME workflow**"; spike must show "a deferred-tool (`requires_approval=True`) workflow **pauses and resumes** correctly across a process restart."

**VERIFIED as real:** `requires_approval=True`, `DeferredToolRequests`, `DeferredToolResults`, `ToolApproved` (with `override_args`), `ToolDenied` (with custom message) all exist in current v2 docs: https://ai.pydantic.dev/deferred-tools/ and https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/. Marketing on both sides explicitly advertises "human-in-the-loop workflows with production-grade reliability" for the DBOS/Temporal integrations.

**FINDING (serious):** the *documented* deferred-tool flow does **not** pause a run. When the model calls a `requires_approval` tool, **the agent run ENDS** with a `DeferredToolRequests` output object; the caller then starts a **NEW agent run** with the original run's **message history** plus a `DeferredToolResults` object (deferred-tools doc, ibid.). Under `DBOSAgent`, that means the first workflow **completes** and approval triggers a **second workflow** — there is no documented "paused workflow resumed by DeferredToolResults" primitive for DBOS. Two viable implementations exist, and the spike must pick and test one:
  (a) **Two-workflow bridge:** persist message history (by reference into turn_log — see §3), approval event starts run #2 with history + results. Simple, matches docs exactly.
  (b) **In-workflow blocking:** v2's `HandleDeferredToolCalls` capability (handler receives `DeferredToolRequests`, returns `DeferredToolResults`, run continues in a single call — https://pydantic.dev/docs/ai/api/pydantic-ai/capabilities/) with the handler implemented as a DBOS step that blocks on a DBOS notification/event (`DBOS.recv`) until the asesora decides. This is the only shape that literally matches "resumes the SAME workflow" — and a workflow blocked for days interacts with the versioning finding in §4.
Neither is exotic; both are buildable. But the spike rubric as written tests a primitive that does not exist in the documented API shape, so a naive spike could "fail" (or worse, "pass" a misconceived hack). **Mandatory fix: rewrite spike item (b)** to test the documented pattern(s), across process restart AND across an app-version change (§4).

Open GitHub issues confirm active movement in exactly this area (e.g. #3959 `deferred_handler` inline resolution, #3488 user_prompt with deferred approval, #4302 nested deferred calls — https://github.com/pydantic/pydantic-ai/issues/3959) — functional, but a young surface. Pin versions.

## 3. G4 ("schema-level no-raw-text rule for workflow state") — STRUCTURALLY IMPOSSIBLE for the conversation reactor as documented

**Claim (synthesis G4):** "workflow input/step-output Pydantic models expose no free-text fields — only typed references… Closes the checkpoint-blob PHI/erasure gap for good."

**FINDING (serious — the sharpest in this lane):** `DBOSAgent` **by documented design** checkpoints (via pickle, into Postgres) the workflow's inputs and every step's output — and for a conversational turn those ARE raw text: the workflow input is the user prompt (+ message history if passed), and each model-request step's output is the model response (https://pydantic.dev/docs/ai/integrations/durable_execution/dbos/: "DBOS checkpoints workflow inputs/outputs and step outputs into a database using pickle"). You cannot run a patient turn through `DBOSAgent` without raw patient text landing in DBOS system tables. G4's CI check over workflow signatures cannot see inside `DBOSAgent`'s own wrapping. The compliance judge's tiebreak rationale ("C2's payload-by-reference rule closes the checkpoint-blob PHI gap") is therefore only true for the workflows the team writes by hand (cadence, saga, write-plan) — **not for the turn workflows that carry ~100% of the PHI.**

**This does not break the base — DBOS ships the honest fix:** completed-workflow history is deletable/GC-able. `DBOS.delete_workflow` removes a workflow and all inputs/outputs/step results irreversibly; retention thresholds (time-based and rows-based) exist for workflow history (https://docs.dbos.dev/python/tutorials/workflow-management; https://docs.dbos.dev/production/dbos-cloud/retention — the console page is Cloud, but the underlying deletion/GC APIs are library-level and self-hostable; worst case it is plain SQL on the system tables in our own Postgres). **Mandatory fix: amend G4** — (i) scope the no-raw-text CI rule to hand-written workflows; (ii) add DBOS system tables to the retention/erasure design: scheduled GC of completed turn-workflow checkpoints on a short clock (e.g. 7–30 days, inside the 30-day unconsented-health-turn window), and `DBOS.delete_workflow` wired into the GDPR Art. 17 erasure path; (iii) include DBOS system tables in the nightly pg_dump *and* in the purge jobs (backups inherit the retention problem).

## 4. DBOS Transact facts — license, version, Postgres, and the deploy-versioning story

- **License MIT: VERIFIED** (https://github.com/dbos-inc/dbos-transact-py). **v2.26.0 released 2026-06-30: VERIFIED** (same repo, 72 releases, active). C1's Gate note is accurate. Star count ~1.5k — a young single-vendor OSS project, as both candidates already flag.
- **Postgres compat: VERIFIED workable** — "built on top of Postgres," no extension required, SQLite for dev; the existing `pgvector/pgvector:pg16` image needs nothing new. "No additional infrastructure to configure or manage" — verbatim in repo/docs (https://docs.dbos.dev/architecture).
- **Deploy-versioning: VERIFIED as a real, documented mechanism — and it is heavier than a spike checkbox.** DBOS computes an application version as a checksum of workflow code (overridable via `DBOS__APPVERSION`); each workflow is tagged with the version that started it; **recovery only touches workflows whose version matches the running code** (https://docs.dbos.dev/production/self-hosting/workflow-recovery). Official strategies for upgrading with in-flight workflows: **patching** or **versioned blue-green deploys** — "retain some processes running your old code version… while your old processes drain" (https://docs.dbos.dev/java/tutorials/upgrading-workflows — same semantics across SDKs). C2 marked this UNVERIFIED; it is now verified, which cuts both ways: the mechanism exists (good), and on a **single droplet with one gutty-core process and a 1–3 person team deploying weekly**, every deploy that touches workflow code either (a) strands crashed in-flight multi-day workflows (old-version workflows are not recovered by the new process), (b) requires running two process versions side-by-side to drain, or (c) requires explicit fork/patch surgery. Cadence enrollments sleeping for days and approval-blocked workflows (§2 option b) maximize the in-flight surface. **Mandatory fixes:** a written deploy runbook (version policy, drain-or-fork procedure) as a Stage-0 deliverable; and a design law for the cadence engine: **short-lived workflows + DB-state enrollments woken by scheduled ticks** (C1's L6 shape: `next_run_at` + sweeper) rather than one months-long durable-sleep workflow per lead — this shrinks in-flight-across-deploy exposure to minutes. Note the irony: on this specific axis the C1 cadence design is *more* robust than C2's "one enrollment workflow per lead with durable sleep"; the merged plan should adopt C1's shape on C2's substrate.

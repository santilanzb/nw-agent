## 1. WAHA/NOWEB ban risk in 2026 — evidence, not folklore

**What WAHA is.** WAHA's NOWEB engine speaks the WhatsApp Web multidevice protocol (Baileys-class), i.e. it impersonates a linked device on a normal WhatsApp account. This is explicitly against WhatsApp ToS (unofficial/automated clients prohibited), and WAHA's own docs carry a dedicated "How to Avoid Blocking" guide — the maintainers themselves treat bans as an operational reality, not FUD (https://waha.devlike.pro/docs/overview/faq/).

**Real 2025–2026 ban reports (primary evidence, Baileys tracker):**
- "High number of bans on WhatsApp!" — WhiskeySockets/Baileys #1869 (Oct 2025): multiple bots banned in a single week, including reports that WhatsApp "found a way to block users who use Baileys" (https://github.com/WhiskeySockets/Baileys/issues/1869)
- "[BUG] WhatsApp number banning" #1983 (Oct 2025); "Repeated Number Bans" #2075 (Nov 2025); "GETTING BANNED" #2260 (Jan 2026); permanent ban on status upload #2309 (Jan 2026) (https://github.com/WhiskeySockets/Baileys/issues/1983, /2075, /2260, /2309)
- An entire ecosystem of "anti-ban middleware" now exists (https://github.com/kobie3717/baileys-antiban) — a strong tell that ban pressure increased through 2025–26.

**Detection posture 2026.** Industry write-ups describe device fingerprinting at registration, behavioral analysis, user-report signals, and a 2026 addition: unanswered-message counting (too many outbound messages without replies flags the account) (https://achiya-automation.com/en/blog/whatsapp-spam-detection-2026/). A claim that "68% of Indian businesses using unofficial tools report ≥1 ban event in 12 months, per Meta's 2025 Policy Enforcement Report" circulates (https://blog.kraya-ai.com/whatsapp-automation-ban-risk) — **UNVERIFIED** (no such Meta report located; treat as directional only).

**Bottom line for THIS system.** The brief's F8 cadence engine ("first contact within minutes" to every new lead, spaced follow-ups) is precisely the highest-risk fingerprint for unofficial clients: high-volume outbound to numbers that have never messaged you, with a predictable low reply rate — the exact signal the 2026 unanswered-message heuristic targets. The old "15–30%/yr" folklore is if anything *understated for proactive outbound in 2026*; the GitHub record shows recurring 24-hour soft bans escalating to permanent bans within weeks under bot-like outbound. **Inbound-only, human-paced customer service on WAHA remains comparatively survivable; outbound cadence on WAHA is not a responsible design.** A ban also destroys the number itself (reputational asset + printed on materials), not just the session.

**Compliance interaction (feeds R8).** WAHA is a ToS breach carrying patient-adjacent conversations; if Meta bans mid-conversation there is no recourse, and the breach itself worsens any GDPR accountability story. Note the transport choice does NOT solve PHI: Meta does not sign HIPAA BAAs for WhatsApp on either path — the PHI mitigation must live in what Gutty stores/sends, not in transport selection. **UNVERIFIED** in the narrow sense that Meta's BAA refusal is inferred from absence of any BAA offering in WhatsApp Business terms; no public Meta statement found either way.

## 2. Official Cloud API — 2026 pricing model (per-message, changed July 2025)

- Since **July 1, 2025** Meta bills **per delivered template message**, not per conversation (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Categories: **marketing** (always charged), **utility** (charged, but FREE inside the 24-h customer-service window), **authentication**, **service** (non-template replies inside a user-initiated 24-h window — free).
- **Rest of Latin America** rate group (includes **Venezuela**, Ecuador, Panama, etc.): indicative **marketing ≈ $0.0625/msg**, **utility ≈ $0.0080/msg** (https://www.go4whatsup.com/guides/meta-whatsapp-pricing/, cross-read with Meta's rate-card page above). The brief's "$0.074" figure is stale; rate cards update quarterly (next July 1, 2026) — treat $0.06–0.08 as the planning band. Colombia's utility rate is as low as $0.0008 (https://ezcontact.ai/en/blog/whatsapp-api-pricing-comparison-meta-twilio-360dialog-ezcontact/) — rates are heavily country-code dependent, and NutriWhite's base spans VE + diaspora (US $0.025 marketing).
- **Free entry point (FEP) window:** a user arriving via click-to-WhatsApp ad or FB Page CTA, answered within 24 h, opens a **72-hour window where ALL message types are free** (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- **Watch item:** third-party summaries claim some in-window free treatment ends **Oct 1, 2026** ("Meta starts charging for messages sent inside the customer service window") (https://blueticks.co/blog/whatsapp-business-api-pricing-2026) — **UNVERIFIED against Meta's own page**, which still lists CSW non-template messages as free; re-verify before modeling H2-2026 costs.

**Cost model at 1,000 leads/mo (F8 cadence, planning-grade):** assume 4 marketing-template touches per lead not inside any free window: 4,000 × $0.0625 ≈ **$250/mo worst case**. Realistically lower: CTWA-sourced leads (the IG funnel, §4) start inside a 72-h all-free window covering the critical "first minutes + day-1/2 follow-ups"; replies convert the thread to a free service window; utility-classed messages (appointment/exam logistics, quote delivery) are ~8× cheaper than marketing. Realistic band **$80–250/mo** in templates at 1k leads/mo — inside the brief's budget once infra is netted.

## 3. Coexistence and number migration

- **Two different numbers = trivially coexistent.** A WAHA-paired number and a Cloud API number are independent accounts; nothing technically links them. No documented case found of Meta punishing a business's official WABA because a sibling number runs an unofficial client (**UNVERIFIED** as a guarantee — it's an absence of evidence).
- **Same number, both worlds — Meta's "Coexistence" product (2025+):** a number actively used in the **WhatsApp Business App** can onboard to Cloud API **without deleting the app account**; chat history is preserved and both the app and the API work concurrently. Eligibility is Meta-gated (account tenure, quality history) and requires an onboarding-supporting solution provider (https://developers.facebook.com/docs/whatsapp/cloud-api/get-started/migrate-existing-whatsapp-number-to-a-business-account/, https://woztell.com/whatsapp-business-vs-cloud-api-migration-coexistence/, https://respond.io/help/whatsapp/phone-number-migration-to-whatsapp-cloud-api).
- **Hard migration path:** delete the app/WAHA account → register the number on Cloud API. **Chat history is lost** and the number can't return to the Business App unless deregistered from Cloud API (same Meta doc). For Gutty: the FSM's state lives in Postgres keyed on E.164 phone, so *system* memory survives; only in-phone WhatsApp history is lost.
- **Practical route for NutriWhite:** the production Gutty number currently rides OpenClaw/WAHA (a linked-device session on a normal account). Cleanest sequence: (1) stand up Cloud API on a **new number** for all F8 outbound + new-lead funnels immediately; (2) migrate the legacy Gutty number to Cloud API at cutover (hard migration acceptable — Postgres holds state), or via Coexistence if the number is on the Business App and Meta deems it eligible.
- **Group-chat caveat (affects current design):** the team-coordination features (`@Gutty tomo +phone` in `HANDOFF_TEAM_GROUP_JID`) depend on WhatsApp **group** participation, which the Cloud API does **not** support (no group messaging on the Business Platform — **UNVERIFIED against a single canonical doc, but consistently absent from Cloud API reference**). After cutover, team coordination must move to a real inbox/ticket UI (Chatwoot per v2, or the F3 ticket system) or a low-volume internal WAHA session on a non-customer number (internal, human-paced traffic = minimal ban exposure).

## 4. BSP choice — Meta direct vs Twilio vs 360dialog (2026 fees)

| Option | Platform fee | Per-message markup | Notes |
|---|---|---|---|
| **Meta Cloud API direct** | $0 | $0 (Meta rates only) | You build/host webhooks — agent-core already IS a webhook service (`/webhooks/waha` → add `/webhooks/meta`). On-prem API deprecated 2025; "the API" = Cloud API now. (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing) |
| **Twilio** | none | ~+$0.005–0.010/msg | Adds Content API, delivery tooling, and — key later — **WhatsApp Business Calling on Twilio Voice, GA**, wired into ConversationRelay for AI voice (https://www.twilio.com/en-us/blog/products/launches/generally-available-whatsapp-business-calling-twilio-voice, https://ezcontact.ai/en/blog/whatsapp-api-pricing-comparison-meta-twilio-360dialog-ezcontact/) |
| **360dialog** | €49/mo (base tier; per-number fees vary by plan) | $0 markup | Pays off only at volumes where Twilio's markup > €49/mo (~10k msgs/mo); EU processor posture may help the GDPR story (https://360dialog.com/pricing, https://ezcontact.ai/en/blog/whatsapp-bsp-comparison/) |

**Verdict:** with an in-house FastAPI webhook stack already running, **Meta direct is the right default** — zero markup, zero platform fee, first-party rate card, and direct access to new surfaces (Calling API, Marketing Messages max-price caps). Twilio is the fallback if the team later wants managed voice (ConversationRelay) without running WebRTC infra; 360dialog only wins at ≳10k paid msgs/mo, above the 10× headroom point.

## 5. IG → WhatsApp funnel mechanics (F7/F10 intake)

- **Click-to-WhatsApp ads (CTWA)** on IG/FB: user taps ad → lands in WhatsApp thread. Billing bonus: business replies within 24 h → **72-h free entry point window** (all message types free) (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing, https://help.sleekflow.io/en_US/whatsapp/understanding-click-to-whatsapp-ads-ctwa-and-the-72-hour-free-window). Attribution: the inbound webhook carries a **`referral` object with `ctwa_clid`** (Meta click ID) + ad IDs; feed `ctwa_clid` back into Meta Conversions API to attribute deals→ads and let Meta optimize on real outcomes (https://www.twilio.com/en-us/blog/products/2026-guide-to-create-ads-that-click-to-whatsapp-with-twilio). **This only exists on the official API — WAHA gets no referral metadata.**
- **ManyChat / IG DM automation → wa.me:** wa.me has **no native ref parameter**; attribution rides in the **prefilled text** (`wa.me/<E164>?text=<msg with code>`) which arrives verbatim as the user's first message (https://elido.app/en/blog/whatsapp-business-deep-links, https://www.appsflyer.com/blog/deep-linking/whatsapp-deep-link/). ManyChat's own "WhatsApp Ref URL" trigger uses exactly this keyword-in-prefill mechanism (https://help.manychat.com/hc/en-us/articles/20083006204444-WhatsApp-Ref-URL-Trigger). Prefilled text also lifts tap→send conversion ~30–50% (vendor claim, https://elido.app/en/blog/whatsapp-business-deep-links — **UNVERIFIED**).
- **Design consequence for agent-core:** the inbound normalizer must extract source attribution from (a) the `referral`/`ctwa_clid` object, (b) a ref-code grammar in first-message prefill (e.g. `[src:ig-story-jul]`... or a human-invisible keyword), and stamp it onto the lead record at intake (R1's identity resolution consumes it). Current `normalize_waha_event()` (waha.py:22) captures none of this — a Cloud API adapter should emit a richer normalized message (channel, referral, media) from day one.

## 6. Voice seam — what to stub now (F8 call-touch → Fase 2+ voice agent)

**The 2026 headline: WhatsApp Business Calling API is GA on Cloud API.** Voice calls happen *inside the existing WhatsApp thread* — no PSTN, no second identity. User-initiated calls work everywhere Cloud API does; business-initiated calls work in most countries (blocked when the *business* number is US/CA/EG/VN/NG — NutriWhite's VE/LatAm numbers are fine). Billing: inbound calls free; outbound per-minute in 6-second increments, tiered (https://developers.facebook.com/documentation/business-messaging/whatsapp/calling/pricing, https://respond.io/whatsapp-business-calling-api). Meta frames the API as paving the way for AI voice support (https://mobileecosystemforum.com/2025/12/17/whatsapp-opens-a-new-front-in-business-voice-with-calling-api/). **This is decisive for transport choice: a voice agent on WhatsApp is only reachable via the official Cloud API — WAHA has no calling surface.** For a Venezuelan patient base (where WhatsApp calls, not PSTN, are the default phone), this is the natural voice channel.

**Agent plumbing exists off the shelf:** Pipecat ships a first-class WhatsApp Calling integration (Cloud API token + `calls` webhook field + WebRTC `SmallWebRTCTransport`; inbound calls documented today) (https://docs.pipecat.ai/pipecat/features/whatsapp); LiveKit provides connectors bridging WhatsApp Business voice into rooms (https://docs.livekit.io/telephony/); Twilio Voice + ConversationRelay is the managed path (https://www.twilio.com/en-us/blog/products/launches/generally-available-whatsapp-business-calling-twilio-voice).

**VE-Spanish ASR/TTS maturity (2026):** latency is solved — ElevenLabs Flash ~75 ms TTFA, Deepgram Aura-2 ~90 ms TTS / ~150–184 ms streaming ASR first-words; full voice loop under ~300 ms is production-normal (https://gradium.ai/content/stt-api-benchmark-2026-latency-accuracy, https://www.cekura.ai/blogs/best-tts-for-ai-voice-agents). Spanish is broadly supported (Deepgram 30+ langs, ElevenLabs 32, Azure 140+), **but** benchmarks are English-centric; documented failure modes include per-call language pinning and English-defaulted entity pronunciation in Spanish calls (https://deepgram.com/learn/using-elevenlabs-multilingual-voice-agents-limitations, https://www.coval.ai/blog/best-text-to-speech-providers-in-2026-independent-benchmarks-and-how-to-choose/). No VE-register benchmark exists; treat Venezuelan-Spanish voice quality as **unproven → pilot-gated**, consistent with the brief's mode-3-first philosophy (voice launches as human-call-prep tasks; a voice agent must pass eval gates on recorded pilots).

**Seam to stub NOW (zero core changes later):**
1. **Transport protocol** (replaces the concrete `WahaClient` dependency): `send_text`, `send_template(name, params, category)`, `parse_inbound → NormalizedInbound{channel, e164, text, media[], referral{ctwa_clid, ref_code}, raw}`. WAHA and Cloud API become two adapters; the FSM keys on E.164 (it already does — `waha.py:_e164`), so the swap is invisible to routing/state.
2. **Touch-type enum in the cadence engine** (F8): `TOUCH_TEXT_TEMPLATE | TOUCH_TEXT_FREEFORM | TOUCH_CALL`. Today `TOUCH_CALL` resolves to a *human call task* (script + context package into the F3 ticket system). Later it resolves to `VoiceAgentAdapter` behind the same interface — the cadence scheduler, CRM writes, and eval hooks never change.
3. **Call-event webhook route reserved** (`/webhooks/meta` handling both `messages` and `calls` fields) so enabling calling is a config flip, not a route redesign.
4. **Conversation-artifact contract**: every touch (text or voice) must emit the same `turn_log` shape (transcript, intent, outcome) — voice adds ASR transcript as the `text` field; downstream (learning loop, evals, Langfuse) stays untouched.

## 7. Recommendation (R7 scope)

**Adopt Meta Cloud API direct as the primary transport for all NEW-lead and proactive traffic immediately; treat WAHA as a legacy-inbound bridge with a scheduled retirement.** Concretely: (a) new Cloud API number for F8 cadences + CTWA funnels now (referral attribution + 72-h free windows + template legality only exist there); (b) migrate the production Gutty number at Stage-3 cutover (hard migration is fine — state lives in Postgres; use Coexistence only if the number is on the Business App and Meta grants eligibility); (c) move team coordination off WhatsApp groups (Cloud API can't join them) into the F3 ticket/inbox surface; (d) stub the Transport protocol + `TOUCH_CALL` task type now so the WhatsApp Calling API voice agent (Pipecat-class, VE-Spanish pilot-gated) plugs in at Fase 2+ without core changes. BSP: Meta direct; revisit Twilio only if managed voice infra is preferred over self-hosted WebRTC.

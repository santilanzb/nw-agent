## 2. Attacks on C2 (each verified or flagged)

### A1 — FATAL-TO-THE-MARGIN: the compliance tiebreak rests on a rule the chosen integration structurally violates

The synthesis (§1.2) says the compliance-precision judge broke the C1/C2 tie **for C2** because "the payload-by-reference rule keeps PHI out of checkpoint blobs (a GDPR Art.17 erasure gap C1-as-written leaves open)," hardened by graft G4 into "workflow input/step-output Pydantic models expose no free-text fields."

But C2's core commitment is `DBOSAgent`, which — per the official integration docs, fetched 2026-07-10 — "automatically converts agent.run() into a durable DBOS workflow and **wraps model calls... as checkpointed steps**," and requires that inputs/outputs be "serializable using **pickle**" (https://pydantic.dev/docs/ai/integrations/durable_execution/dbos/; https://docs.dbos.dev/integrations/pydantic-ai). A model request **is** the message history: the patient's raw Spanish text, symptoms included, is the input to the very step DBOSAgent auto-checkpoints; the model's reply is its output. Therefore, for every LLM-composed care-class turn, **raw conversational PHI lands in pickled DBOS checkpoint blobs by construction** — opaque to the retention workflows, exactly the Art.17 erasure gap the judge penalized C1 and C3 for.

C2 has only two exits, and both cost it the crown:
- **(a)** Run agents *unwrapped* and put only side-effect steps in workflows → the "one execution model" thesis collapses to precisely C1's/C3's posture (durable substrate beside a non-durable agent loop), and the Stage-0 spike's central object (`DBOSAgent`) becomes decorative.
- **(b)** Accept raw text in checkpoints and wire checkpoint-blob purges → G4 as specified ("no free-text fields... CI check over workflow signatures") is unenforceable against auto-generated model-request steps, and C2 now owns the same second-PHI-store problem it attacked C3's Chatwoot for — except Chatwoot stores conversations in *queryable relational rows* with documented deletion APIs, while DBOS stores them in *pickle blobs*.

The synthesis half-saw this: its own stress-test #4 asks the red team to "hunt a code path where raw message text lands in a DBOS checkpoint blob despite the no-text rule (e.g., ... **agent message history**)." The answer requires no hunting: it is the documented default behavior of the integration C2 is named after. **Severity: fatal** to the 0.07 margin — remove the erasure-gap tiebreak and the scoreboard's own numbers make C1 the winner, and the C2-vs-C3 comparison must be re-scored on the same "second PHI store" standard that cost C3 its Pragmatism points.

### A2 — SERIOUS: C2's framework bet is 17 days old, with a contractual 3-month breaking-change horizon

Verified 2026-07-10: **Pydantic AI V2.0 was released June 23, 2026** (version-policy page, https://pydantic.dev/docs/ai/project/version-policy/), i.e. **17 days before this tournament**. The same page commits only to a **3-month minimum** before the next major ("deprecated ... not removed until the next major version, which we won't release sooner than 3 months after V2.0") — and the v2 announcement states the no-breaking-changes window was deliberately **shortened from six months to three** (https://pydantic.dev/articles/pydantic-ai-v2). C2's own document records **v2.6.0 on 2026-07-08** — six minor releases in fifteen days. Features in "beta modules" carry no stability guarantee at all ("very possible that changes ... will not be backward-compatible" — version-policy page).

Consequences for THIS business:
- C2's build is 11–15 engineer-weeks. **The v3 breaking-change window legally opens (~Sept 23, 2026) before C2's Stage 4 ships.** A solo developer can be forced into a major-version migration mid-build of the system that runs the company's revenue channel.
- The Pragmatism·Risk score of **6.0** — the worst of the top three candidates, the largest single-lens gap in the study (C1: 8.0) — already priced framework churn as a *possibility*. The verified release cadence makes it a *base rate*.
- C3 consumes **zero** Pydantic-AI surface. Its DBOS usage is confined to the mature, load-bearing core (scheduled workflows, durable sleep, checkpointed steps, queues — the surface R5 verified against https://docs.dbos.dev/architecture), not the newest integration in the pairing. C3 buys C2's genuinely good idea (durable time + exactly-once substrate) exactly where it is proven and declines it where it is weeks old.

### A3 — SERIOUS: the "single HITL primitive" — the mechanism the whole autonomy ladder runs on — is undocumented in the integration C2 commits to

Pydantic AI's deferred tools **end the agent run** with a `DeferredToolRequests` output; approval resumption means constructing `DeferredToolResults` and starting a **new run with the prior message history** (https://ai.pydantic.dev/deferred-tools/, verified via search 2026-07-10). C2's architecture diagram instead claims "asesora approves in team surface → `DeferredToolResults` **resumes the SAME workflow**." Whether a DBOS workflow can pause on a deferred-tool output and resume across a process restart is exactly what C2 lists as open question §12.2 — and the official DBOS-integration documentation, fetched 2026-07-10, **"does not explicitly address in-flight workflow versioning or human-in-the-loop/deferred tools behavior"** (https://pydantic.dev/docs/ai/integrations/durable_execution/dbos/). The synthesis calls this "the load-bearing hinge of the whole verdict" (its stress-test #1).

So the tournament's provisional winner hangs on an undocumented interaction between a 17-day-old major and a young durable-execution library — gated by a two-week spike whose *fallback is C1, not C2*. By the synthesis's own conditions, C2 is not "the winner"; it is **a bet that, if lost, crowns C1**. C3, by contrast, needs no spike: its approval surface (Chatwoot conversation status `pending→open`, private-note approvals, Create-Message API) is **documented, shipped product behavior** (https://www.chatwoot.com/hc/user-guide/articles/1677497472-how-to-use-agent-bots), and its deferred writes ride the CrmWriteGate ask-first ladder that all candidates share.

### A4 — SERIOUS: the synthesis had to rebuild C2 out of C3's parts — and that kills C2's own case against C3

C2's entire §11 argument against C3 is: "adds services a 1–3 person team must operate; C2 adds *zero* services." The synthesis then made **Chatwoot mandatory** (G1: "+1 container set (Rails+Redis+Sidekiq)"), imported C3's measurement plane (G8), and put both on the final stack as L17. The delivered system under the C2-base plan **runs Chatwoot anyway** — one stage later than C3 would, after months of approvals flowing through a WAHA group-command CLI at exactly the throughput ceiling all three judges flagged as the cap on the −80%. The residual architectural difference between "C2+grafts" and "C3 with its designed direct-Cloud-API fallback engaged" (C3 §5: Chatwoot degrades to console+mirror; brain keeps direct ingress/egress — a config change C3 pre-designed) is essentially **where the turn loop lives**: a ported ~400-line workflow on a 17-day-old framework (C2) vs the proven, punch-list-fixed FSM the eval harness already validates (C3). When the winner needs the loser's centerpiece to be viable, and the loser pre-designed the exact containment mode (mirror-only, never in the send path) that the synthesis adopted as G1's condition, the scoreboard has mis-attributed design credit. **Note also:** C2's specific technical strike against C3 — "n8n specifically fails as cadence owner (missed-tick skips)" — attacks a position C3 never held: C3 rejected n8n as cadence owner explicitly (C3 L7 "Rejected: n8n as cadence owner") and runs cadences on the same DBOS substrate C2 uses. The winning candidate's anti-C3 argument is a strawman.

### A5 — SERIOUS: deploy-versioning tax lands on every turn in C2, not just on sagas

DBOS pins recovery to compatible application versions: "workflows only recover to processes running compatible code," and breaking changes require patch statements or multi-version deploys (https://docs.dbos.dev/architecture, fetched 2026-07-10). This cost exists for any DBOS user — including C3 — but its *surface area scales with what you put inside workflows*. C2 puts **every reactive turn, every agent run, every cadence touch and saga** inside workflows; a solo developer shipping weekly with 4-touch/14-day cadences and multi-day quote follow-ups permanently in flight lives in the patching/versioning regime for the entire codebase, on a single droplet where running old-version processes side-by-side is not realistic. C3 confines workflow payloads to its own tiny typed rows (enrollment ids, step numbers, quote ledger keys) and keeps the reactive hot path *outside* durable execution — a deploy can never strand a live conversation. INFERENCE (structural, from verified versioning semantics): pickle-serialized Pydantic-AI message objects checkpointed under v2.x may fail to unpickle after a library upgrade while multi-day workflows are in flight — churn (A2) and pickle (A1) compound precisely on C2's largest surface. UNVERIFIED as a demonstrated failure; the spike should test an upgrade, not just a crash.

### A6 — MINOR: bus factor and the 3 a.m. question

C2's failure modes at 3 a.m. live inside DBOSAgent/DBOS recovery semantics — knowledge that exists, today, in one developer's head and in a documentation set that (verified above) does not yet cover the failure mode in question. C3's 3 a.m. failure modes are: a Rails inbox is down (asesoras lose the console; the brain keeps answering via direct Cloud API — C3 §10 R1), an n8n flow failed (nightly reconciliation catches it; blast radius = intake and reports), a DBOS saga stalled (same as C2, smaller surface). Chatwoot and LiteLLM have communities in the tens of thousands of deployments with web-searchable failure modes and hireable operators; `DBOSAgent` has a documentation page dated weeks ago. For a 1–3 person team with no platform hire, "googleable at 3 a.m." is an availability property.

### A7 — MINOR: the precision-lens gap (8.33 vs 6.33) overstates a difference both candidates concede is bounded elsewhere

C2's own §6: "literal exactly-once does not exist against external APIs; C2 delivers effectively-once... the *need* for [idempotency guards] is identical in every candidate." C3's §5 says the same and implements the same four guards (durable inbox UNIQUE(source,event_id); `send_intents` outbox written before transport; `crm_write_log` WAL with deterministic keys; `facts/prices.yaml` + dollar guard). C2's genuine advantage is *uniformity of pattern* (workflow-derived keys vs per-seam keys); that is worth something, but a 2-point lens gap priced it as if C2 had a stronger *guarantee*, which C2 itself denies. And per A1, C2's uniformity claim is partly hollow: custom tools "are **not** automatically wrapped by DBOS" — each side-effect step still needs the developer to decorate and guard it by hand (https://pydantic.dev/docs/ai/integrations/durable_execution/dbos/), which is per-seam craftsmanship under another name. Also verified on the same page: DBOS retries can **compound with Pydantic AI's own request retries** unless provider clients are manually set to `max_retries=0` — a new double-execution footgun class that exists only in the C2 pairing.

## 6. Honest concession — where C2 genuinely beats C3

Three things, stated without hedging. **First**, if the Stage-0 spike passes cleanly — DBOSAgent recovery, deferred-tool resumption across restarts, versioned deploys with in-flight workflows, and a demonstrated answer to the checkpoint-PHI problem (A1) — then C2's compounding argument is real and better than C3's: framework-typed packages that fail at import, one durability pattern inherited by every future function, and HITL/model-routing as maintained code beat C3's convention-enforced package contract and its enumerated-but-real integration seams. The mission sentence is "continuously extensible company brain," and on a passed spike C2 services that sentence better. **Second**, C3's hot path carries a genuine unknown C2 does not have: Chatwoot Agent-Bot hop latency and webhook retry/delivery semantics are UNVERIFIED (C3's own §1), and although the direct-ingress fallback is designed, triggering it means C3 converges toward "C1 plus a console" — defensible, but an admission that the hub-topology bet partially failed. **Third**, C3 runs more surfaces (≈6 more containers) and its Pragmatism 5.0, even corrected for the G1 inconsistency (§3.5), does not climb above C1's 8.0: for a team whose true capacity is one FastAPI process, C3 is the wrong risk shape and C1 — not C2 — is the safe harbor. C3's claim is not that it is the safest candidate; it is that it is the candidate whose risks are *bounded, enumerated, and community-shared*, while the winner's decisive risks were unpriced, undocumented, and 17 days old.

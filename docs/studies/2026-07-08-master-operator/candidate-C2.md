# Candidate C2 — "Agent-Platform Ground-Up": One Durable Execution Model on Pydantic AI + DBOS

> **Study:** Cerebro Gutty v3 — Master Operator · **Date:** 2026-07-08 · **Composer:** C2 architect
> **Framework commitment (pick ONE):** **Pydantic AI v2 (typed agent framework) fused with DBOS Transact (durable execution) as a single runtime — `gutty-core` — in which every unit of work (reactive turn, cadence touch, multi-day saga, CRM write plan) is a durable, checkpointed workflow.** Pydantic AI is the "2026 agent framework" of this candidate; DBOS is its execution substrate; the pairing is an *official, documented integration* (`DBOSAgent`), not a bespoke glue layer.
> **Verdict claim:** at operator scope, 8 of 12 functions have zero substrate (recon). The system to build is overwhelmingly *new*; the only thing a rebuild "discards" is a ~300-line reactive FSM carrying 12 punch-list defects. C2 keeps every proven asset (classifier, RAG stack, crm-adapter, handoff schema, Postgres, turn_log/learning schema) and replaces only the orchestration core — with a runtime where durability, typed tool contracts, human-in-the-loop approval, model-agnostic routing, and eval scaffolding are framework primitives instead of hand-written subsystems.

## 0. Thesis

The brief re-opened the v2 verdict because the scope changed shape, not just size (§0). v3 is no longer "a chatbot plus features": reactive chat, proactive cadences, multi-day sagas, and autonomous CRM writes must behave as **one system with one reliability story** — the Precision/Reliability lens (§7.5) demands exactly-once side effects *everywhere*, and the Extensibility lens (§3) demands that a new function ship as a package carrying not just prompts and seeds but *schedules, sagas, write-actions, and evals*.

C1's answer is to keep the hand-rolled FSM and bolt four subsystems around it. That is a respectable answer, but it has a structural consequence C1 itself documents: **durability becomes a sidecar, not the execution model.** In C1, reactive turns run *outside* durable execution ("DBOS is not on the hot path" — C1 L4), and exactly-once is achieved seam-by-seam with hand-placed guards (inbox here, outbox there, WAL over there). Every one of those guards is bespoke correctness-critical code owned forever by a 1–3 person team, and every *future* function package must remember to re-implement the same discipline.

C2's answer: make durability the *default substrate* and make the agent layer *typed framework objects*. Concretely:

- **Every unit of work is a DBOS workflow.** A WhatsApp turn, a cadence touch, a presupuesto saga, a weekly broadcast batch, a CRM write plan — all are workflows whose steps (LLM calls, Zoho writes, WhatsApp sends) are checkpointed in the existing Postgres. Crash mid-anything → resume from the last completed step; "every workflow input and step output is durably stored in the system database" (https://pydantic.dev/docs/ai/integrations/durable_execution/dbos/, fetched 2026-07-08). Exactly-once discipline is *one pattern applied uniformly*, with idempotency keys derived from workflow identity — not N bespoke guards.
- **Every agent is a typed Pydantic AI `Agent`.** Typed tools with validated arguments, structured outputs for slot extraction and write payloads, **deferred tools** (`requires_approval=True` → `DeferredToolRequests` / `ToolApproved` / `ToolDenied`) as the *native* mechanism for the CRM autonomy ladder and mode-3→mode-2 graduation, model-agnostic routing (Anthropic and Gemini behind one interface — honoring brief §4b as a config change), and `pydantic-evals` for the graduation gates. (https://ai.pydantic.dev/deferred-tools/; https://pydantic.dev/docs/ai/overview/)
- **A function package is a typed artifact, not a convention:** `{Agent, toolset, intent seeds, workflows/schedules, eval Dataset, policy manifest}` registered into one runtime. The type system enforces the contract that C1 enforces by registrar discipline.

This is the strongest honest reading of the C2 mandate: not "adopt LangGraph because frameworks are shiny" (R5 demolishes that), but *rebuild the orchestration core on the one 2026 framework pairing that actually provides what this scope lacks — time, exactly-once, typed tool authority, and native HITL — at zero new infrastructure.*

## 1. Why ground-up is the right call at THIS scope

**1.1 The "80% missing" inventory (recon, verified).** F2, F4, F5, F6-writes, F7, F8, F9, F10 have zero substrate; the whole system starts at `POST /webhooks/waha`; there is no scheduler, no outbound path, no identity model, no write authority beyond Notes (`recon-code-seams.md`). F11/F12 are a manual CLI and schema-only stubs. What exists and is *proven* is: the intent classifier (~99% on seeds), the RAG stack, the crm-adapter read layer, the handoff state machine, and the Postgres schema. **None of those are orchestration.** They are services and data — C2 keeps all of them unchanged (L8, L10, L13, L16).

**1.2 What a "rebuild" actually discards.** agent-core is ~1,500 lines; its orchestration heart (`fsm.py`) is ~300 lines carrying, per the brief's own punch-list (§4): in-memory dedup lost on restart, fail-open HMAC, fail-open handoff mute, unbounded ingress tasks, per-turn HTTP clients, a silent first-match registry, raw PHI to Langfuse, no provider seam, dropped media. C1 proposes to fix all 12 in place; C2 observes that **the fix list is approximately a rewrite already** — and that rewriting *onto* a substrate that makes half the list impossible-by-construction (durable inbox dedup, checkpointed side effects, typed registry, provider-agnostic model layer) is the cheaper way to pay the same bill.

**1.3 The false dichotomy.** "Evolve vs rebuild" framing implies a large working system is at stake. The working production system today is *OpenClaw* (pre-cutover); agent-core has never carried production traffic (BRIEF §4: cutover not done, "nothing of the v2 target design is built"). C2's "rebuild" is therefore: port two validated behaviors (F1 turn flow, F3 handoff) into workflow form — with the eval harness as the parity gate — and build the missing ten functions on the new substrate directly. There is no big-bang migration of live traffic; there is one cutover, which the roadmap owes us anyway.

**1.4 Where C2 concedes to C1.** If the scope were *only* F1+F3 (reactive chat), C1 wins outright: the 2026 owned-loop consensus (12-factor agents, https://github.com/humanlayer/12-factor-agents; Anthropic's Building Effective Agents, https://www.anthropic.com/research/building-effective-agents) argues against frameworks for a thin reactive loop, and R5's stress test is unambiguous. C2's claim is that **the consensus's own logic flips at operator scope**: those same sources say "own your control flow" — and a control flow that spans days, survives crashes, and must never double-send is exactly what durable-execution workflows *are*. Pydantic AI adds the smallest defensible agent-framework layer on top: typed tools and outputs (the brief's precision requirement), deferred approvals (the brief's autonomy ladder), and provider-agnostic models (the brief's §4b directive) — while remaining "a thin loop you own" in spirit: agents are plain Python objects; there is no graph DSL, no separate server, no checkpointer file format.

**Honest caveats of the commitment** (the red team will find these; here they are first):

1. **At-least-once steps.** DBOS steps may re-execute after a crash ("if a step fails, it restarts from the beginning") — exactly-once against Meta/Zoho still requires idempotency keys and send-intent guards at the edges (§6). C2's advantage is that keys derive mechanically from workflow identity; the *need* for them is identical in every candidate.
2. **No token streaming inside workflows.** `Agent.run_stream()` is unsupported inside a DBOS workflow (integration doc, verified). Irrelevant for WhatsApp — replies are discrete messages — but it forecloses a future streaming web-chat channel *inside* workflows (that channel would run the same Agent unwrapped).
3. **Serialization discipline.** DBOS pickles workflow inputs/step outputs into Postgres. Two consequences: (a) deploys with in-flight multi-day workflows need version discipline (DBOS pins recovery to application version — operational detail UNVERIFIED, verify in Stage-0 spike); (b) **PHI-bearing payloads land in checkpoint blobs**, which are opaque to retention jobs — so C2 imposes a design rule: *workflow payloads carry references (turn_log row ids, enrollment ids), never raw message text*, keeping redaction/retention (R8) operative on the relational tables that own the text.
4. **Framework churn.** Pydantic AI moved fast to v2. Mitigation: the surface C2 uses is narrow (Agent, tools, deferred tools, models, evals), agents are plain objects testable without DBOS, and both libraries are MIT with state in our own Postgres — worst case is vendoring, not data hostage.

**Why "one execution model" is not a slogan.** In C1, "follow up in 3 days" (cadence), "wait for asesora approval" (ladder), "retry the quote send" (saga), and "don't double-process this webhook" (dedup) are four different mechanisms. In C2 they are one: a workflow that sleeps durably, a workflow paused on a deferred tool result, a workflow step retrying from checkpoint, and a workflow keyed to an inbox row. A new function package that needs any of these inherits them by *writing a workflow*, not by learning four subsystems. That is what "designed from day one as a multi-function operator" buys.

**Latency (brief §3).** The deterministic hot path is: inbox insert (~1–3 ms) → in-process workflow start → classify (embedding call, ~100–300 ms, unchanged from today) → deterministic dispatch → outbox insert + Cloud API send. DBOS checkpoint writes are single local-Postgres inserts (~1–5 ms each, a handful per turn). Deterministic turns stay well under 1 s; LLM-composed turns remain 1–2 s dominated by model latency. No network hop is added anywhere (contrast Temporal Cloud, which adds a WAN round-trip per step).

## 5. The 16-layer stack

Legend: **REUSE** (keep/harden existing asset) · **HYBRID** (existing + significant addition) · **BUILD** (new owned code) · **BUY** (external service/OSS adopted as-is).

### L1 · WhatsApp transport & channels — HYBRID (buy Meta Cloud API direct; WAHA as retiring bridge)
New Cloud API number immediately for ALL business-initiated sends (templates, cadence, quote PDFs, CTWA funnels, F4); legacy Gutty number migrates at cutover (Coexistence if eligible, else hard migration — state lives in Postgres keyed on E.164, https://developers.facebook.com/docs/whatsapp/cloud-api/get-started/migrate-existing-whatsapp-number-to-a-business-account/). WAHA survives only as legacy-inbound + internal team-group bridge with scheduled retirement. **Rationale:** WAHA cannot send templates and proactive outbound on unofficial clients is Meta's canonical ban profile with documented 2025–26 ban waves (R7: https://github.com/devlikeapro/waha/issues/1362, https://github.com/WhiskeySockets/Baileys/issues/1869); Cloud API is also the only path to `ctwa_clid` attribution and the GA WhatsApp Business Calling API (voice seam — https://docs.pipecat.ai/pipecat/features/whatsapp). **Rejected:** WAHA-only (existential ban risk); Twilio BSP (+$0.005–0.010/msg for managed voice we don't need yet); 360dialog (€49/mo wins only ≳10k paid msgs/mo — https://360dialog.com/pricing).

### L2 · Ingress bus & durable inbox — BUILD
Routes `/webhooks/{meta,waha,manychat,zoho}` with per-source signature verification (reusing the `verify_waha_hmac` pattern, fail-closed on empty key), normalizers emitting a transport-neutral `InboundEvent`, and a durable `intake_events` inbox (UNIQUE `source+source_event_id`) inserted **before** the 200 ACK. **The DBOS workflow id is the inbox event id** — redelivery cannot start a second workflow; the punch-list `_SEEN` bug class is impossible by construction. **Rationale:** Meta redelivers on non-2xx; ManyChat likely never retries and cannot enumerate subscribers (R1). A new intake source = a new normalizer posting to the same bus. **Rejected:** n8n as intake glue (second brain, skips missed ticks — R2); iPaaS ($30–80/mo for two webhook routes — R1).

### L3 · Identity broker — BUILD

## 6. Precision & exactly-once (brief §3's explicit requirement)

Honest framing (shared with C1, because it is the truth): literal exactly-once does not exist against external APIs; C2 delivers **effectively-once** — at-least-once execution with deterministic idempotency guards — plus deterministic-only money paths. C2's differentiator is *uniformity*: the guards are one mechanical pattern, not per-seam craftsmanship.

1. **Inbound:** ACK only after durable `intake_events` insert; **workflow id = inbox event id** → redelivery joins the existing workflow instead of starting a new one. Restart recovery is DBOS's core property ("DBOS leverages these checkpoints to recover workflows from their last completed step").
2. **Steps:** every external call is a step; on crash-retry a completed step's recorded output is replayed, not re-executed. The residual window is a crash *mid-step after* the external call landed — closed by guards 3–5.
3. **Outbound sends:** `send_intents` outbox row written in the step *before* the transport call, keyed `(workflow_id, step_seq)` (cadences: `(enrollment_id, step_no)`); the send step first checks intent status; Cloud API message-id stored on success; content-hash dedup window guards the WAHA bridge (which has no idempotency support — mitigated, not solved, and retired with WAHA).
4. **CRM writes:** WriteGate idempotency key `hash(workflow_id|action|canonical_params)` checked in `crm_write_log` before dispatch; Zoho-side belt-and-suspenders via upsert `duplicate_check_fields` (Zoho has no native idempotency mechanism — R3); pre-write snapshots make undo a compensating update; deletes impossible at OAuth scope.
5. **Money:** prices only from `facts/prices.yaml` + Products by id; quote totals computed twice and matched before send; regex output guard blocks any LLM-composed reply containing a dollar amount not in the fact table; discounts escalate, never write. LLM tool arguments are schema-validated (typed tools) before they reach any gate — malformed writes fail at validation, not at Zoho.
6. **Health claims:** approved-claims registry + classifier on 100% of outbound sales turns (sampling cannot catch rare violations — R4).
7. **Verification loop:** `--mode crm` read-after-write evals in CI/sandbox; nightly production reconciliation (every write-dispatching turn must match a Zoho record); mismatch pages the team group and flips the action type to ask-first. Stage-2 acceptance includes chaos tests: kill `gutty-core` mid-saga and assert zero duplicate sends/quotes on recovery — the test C1 must also pass, but C2 runs it against one mechanism instead of four.
